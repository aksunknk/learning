$ サーバ状態 / Query

キャッシュ境界と再検証 — useState にサーバデータを抱え込まない。ライブラリ名より「キー・寿命・真実の所在」を言語化する。

SCOPE

reactarch が「副作用を Abort し、状態を局所化せよ」まで述べた続き。サーバ由来の値はコンポーネント State ではなくキャッシュ層の責務とする。TanStack Query / SWR の API 暗記ではなく、なぜ必要かを説明する章。

01

クライアント状態 vs サーバ状態

▼

真実の所在で分類する

クライアント状態は UI が所有者（入力中テキスト、開閉、選択）。サーバ状態は API / DB が所有者で、クライアントはキャッシュされた写しにすぎない。後者を useState に二重管理すると、画面 A が更新した直後に画面 B の古い fetch が上書きする Race が構造的に起きる。

分類表（面談用）

クライアント状態（UI 所有）:
  - フォーム draft、モーダル open、タブ index
  - 「まだサーバに無い」一時値

サーバ状態（API 所有・キャッシュ）:
  - GET /tasks の一覧、ユーザープロフィール
  - 最終更新時刻・ETag を持つ永続データ

アンチパターン:
  各画面が独自に fetch → setState
  → 同一リソースのコピーが N 箇所に散在
  → invalidate 手段が無い

SRE 視点

障害時に追うのは「どの画面の State が古いか」ではなく「キャッシュキーと再検証がいつ走ったか」。サーバ状態を一箇所に寄せると、観測点がログとキャッシュメタに集約される。

02

stale-while-revalidate とキャッシュキー

▼

古い写しを出しつつ裏で取り直す

stale-while-revalidate（SWR）は「キャッシュを即表示し、背後で再取得して差し替える」。HTTP の Cache-Control: stale-while-revalidate（Web/API 章）と同型の思考を、アプリ内メモリキャッシュに降ろしたもの。

キー設計がすべて

キー = リソースの同一性を表すタプル
  ["tasks", { status: "open" }]
  ["task", id]

ルール:
- 同じキー → 同じキャッシュエントリ（購読者で共有）
- 変異後は関連キーを invalidate / setQueryData
- キーに「今の時刻」を入れない（毎回ミスヒット）

寿命:
  fresh → stale（表示は継続、再検証トリガ）
  → inactive（購読者ゼロで GC 候補）
TypeScript
// 概念: キーと fetcher の対がキャッシュの原子
type QueryKey = readonly unknown[];

type Entry<T> = {
  data?: T;
  error?: unknown;
  updatedAt: number;
  subscribers: Set<() => void>;
};

// staleTime 経過後の read は「即 data + 裏で refetch」
function isStale(entry: Entry<unknown>, staleTime: number) {
  return Date.now() - entry.updatedAt > staleTime;
}

DB の N+1 との対応

コンポーネントごとに個別 fetch するのは、ORM で行ループしながら関連を取る N+1 と同型。キー共有キャッシュは「一括読み」に相当する。一覧キーと詳細キーの無効化範囲を設計で決める。

03

楽観更新とロールバック

▼

UI を先に進め、失敗なら真実へ戻す

楽観更新は「サーバ応答前にキャッシュを書き換える」。失敗時はスナップショットへロールバックするか、invalidate してサーバ真相と再同期する。ロールバック無しの楽観更新は、障害時にクライアントだけ嘘を表示し続ける。

TypeScript
async function toggleDone(cache: Cache, id: string) {
  const key = ["task", id] as const;
  const prev = cache.get<Task>(key); // スナップショット
  if (!prev) return;

  cache.set(key, { ...prev, done: !prev.done }); // 楽観
  try {
    await api.patch(`/tasks/${id}`, { done: !prev.done });
  } catch (e) {
    cache.set(key, prev); // ロールバック
    throw e;
  }
}

競合の観測

同時編集:
  - ETag / updatedAt を PATCH に載せて 409 を取る
  - 409 なら invalidate → 最新を取り直す（黙って上書きしない）

一覧と詳細:
  - 詳細を楽観更新したら一覧キーも整合させる
    （setQueryData で両方、または ["tasks"] を invalidate）
04

実戦 — Query パターンの最小自作実装

▼

ライブラリ無しで原理を固定する

本番は TanStack Query 等でよい。面談では「キー・Entry・購読・stale 再検証・mutate」を自作できるかが問われる。以下は教育用の最小骨格（本番非推奨の簡略化あり）。

TypeScript
type Key = string; // 本番は配列シリアライズ。ここでは簡略

type Entry<T> = {
  data?: T;
  error?: unknown;
  updatedAt: number;
  promise?: Promise<T>;
  listeners: Set<() => void>;
};

class QueryCache {
  private map = new Map<Key, Entry<unknown>>();

  get<T>(key: Key) {
    return this.map.get(key) as Entry<T> | undefined;
  }

  subscribe(key: Key, fn: () => void) {
    let e = this.map.get(key);
    if (!e) {
      e = { updatedAt: 0, listeners: new Set() };
      this.map.set(key, e);
    }
    e.listeners.add(fn);
    return () => e!.listeners.delete(fn);
  }

  private notify(key: Key) {
    this.map.get(key)?.listeners.forEach((l) => l());
  }

  setData<T>(key: Key, data: T) {
    const e = this.get<T>(key) ?? { updatedAt: 0, listeners: new Set() };
    e.data = data;
    e.error = undefined;
    e.updatedAt = Date.now();
    this.map.set(key, e as Entry<unknown>);
    this.notify(key);
  }

  async fetchQuery<T>(
    key: Key,
    fetcher: (signal: AbortSignal) => Promise<T>,
    staleTime = 30_000
  ): Promise<T> {
    const e = this.get<T>(key) ?? { updatedAt: 0, listeners: new Set() };
    this.map.set(key, e as Entry<unknown>);

    const fresh = Date.now() - e.updatedAt <= staleTime && e.data !== undefined;
    if (fresh) return e.data as T;
    if (e.promise) return e.promise as Promise<T>; // 同時購読の合流

    const ac = new AbortController();
    const p = fetcher(ac.signal)
      .then((data) => {
        this.setData(key, data);
        e.promise = undefined;
        return data;
      })
      .catch((err) => {
        e.error = err;
        e.promise = undefined;
        this.notify(key);
        throw err;
      });
    e.promise = p as Promise<unknown>;
    return p;
  }

  invalidate(key: Key) {
    const e = this.get(key);
    if (!e) return;
    e.updatedAt = 0; // 即 stale → 次の fetchQuery で再取得
    this.notify(key);
  }
}

// React 側（概念）: subscribe で再レンダー、mount で fetchQuery

面談で一言で言うなら

「サーバ状態はキー付きキャッシュ。表示は SWR、更新は楽観＋ロールバック。コンポーネントは購読者であり所有者ではない。」
