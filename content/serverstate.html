$ サーバ状態 / Query

API から取ってきたデータを、画面コンポーネントの useState に抱え込まないための考え方です。ライブラリ（TanStack Query など）の使い方暗記より、「データの持ち主は誰か」「古い写しをどう扱うか」を言葉にできるようにします。

この章の位置づけ

前の「CFG / UI防衛」章では、非同期通信の打ち切り（Abort）や、状態をできるだけ狭い範囲に置く話まで触れました。その続きです。サーバ（API・データベース）に本体があるデータは、各画面がバラバラに useState で持つより、アプリ内の共有キャッシュ（あとで説明する Query 層）に置く方が事故が減ります。有名ライブラリの API を覚える章ではなく、「なぜその層が必要か」を説明する章です。

01

クライアント状態 vs サーバ状態

▼

「データの持ち主」で二種類に分ける

画面に出る値はすべて同じではありません。クライアント状態とは、ブラウザ上の UI だけが知っていればよい一時的な値です。例: 入力フォームに打ち込んでいる途中の文字、モーダル（ポップアップ）が開いているかどうか、今どのタブを選んでいるか。これらはまだサーバに保存されていなくてもよく、持ち主は「その画面」です。

一方 サーバ状態とは、本当の持ち主が API やデータベース側にあるデータです。例: タスク一覧、ユーザーのプロフィール、注文履歴。ブラウザが見ているのは「サーバからコピーしてきた写し（キャッシュ）」にすぎません。ここでいうキャッシュとは、「一度取った結果をしばらく手元に覚えておき、すぐ同じ画面を描画できるようにする仕組み」のことです。

サーバ状態まで各画面が useState で二重に持つと、次のような事故が起きやすくなります。画面 A が最新に更新した直後に、画面 B が少し前に始めた通信（fetch）の古い結果で上書きする——いわゆる Race Condition（競合状態）です。複数の非同期処理が、到着順によって意図しない結果になる現象を指します。

用語メモ

useState … React で「画面が覚えておく値」を持つ仕組み
fetch    … ブラウザから API（サーバ）へ HTTP リクエストを送る関数
キャッシュ … 写しを手元に残すこと。本体はサーバ側にある前提
invalidate（無効化）… 「この写しは古い」と印を付け、次は取り直すこと

分類の具体例

クライアント状態（UI が持ち主）:
  - フォームの下書きテキスト
  - モーダルの開閉
  - タブの選択位置
  - 「まだサーバに送っていない」一時的な値

サーバ状態（API / DB が持ち主・ブラウザは写し）:
  - GET /tasks で取ったタスク一覧
  - ログイン中ユーザーのプロフィール
  - 最終更新時刻などが付いた永続データ

やりがちな失敗:
  画面ごとに各自が fetch → setState
  → 同じデータのコピーが何箇所にも散らばる
  → 「全部まとめて古くなったと印を付ける」手段が無い

障害調査の視点

本番で「画面が古い」と問い合わせが来たとき、「どのコンポーネントの State が悪いか」を一つずつ探すより、「どのキャッシュのキーで、いつ再取得が走ったか」を追える設計の方が調査が速いです。サーバ状態を一箇所（キャッシュ層）に寄せると、観測点もそこに集まります。

02

stale-while-revalidate とキャッシュキー

▼

古い写しを先に出し、裏で取り直す

stale-while-revalidate（略して SWR）は英語のまま覚えるより、意味で覚える方がよいです。stale は「賞味期限が切れた／古くなった」、revalidate は「もう一度確かめて更新する」です。合わせると「まず手元の（少し古い可能性のある）写しを画面に出し、その裏でサーバに最新を取りに行き、届いたら差し替える」という戦略です。

ユーザーは待ちスピナーばかり見なくて済み、裏では新鮮さに寄せていく、というトレードオフです。HTTP レスポンスヘッダの Cache-Control: stale-while-revalidate（ブラウザや CDN が使う仕組み。Web/API 章）と同じ考え方を、アプリのメモリ上のキャッシュにも持ち込んだものだ、と捉えるとつながりやすいです。

キャッシュキーとは何か

キャッシュキーは、「この写しは何のデータのコピーか」を表す名前札です。配列で ["tasks", { status: "open" }] や ["task", id] のように書くことが多いです。同じキーを使う画面は同じ写しを共有します。キーが違えば別物として扱われます。

ルールのイメージ:
- 同じキー → 同じキャッシュ枠（複数画面が購読＝聞き役になる）
- データを更新（作成・変更・削除）したあと
  → 関係するキーを invalidate（「古い」印）するか、
    手元の写しを正しい値に書き換える
- キーに「いまの時刻」を入れない
  → 入れると毎回別名になり、キャッシュが効かない（ミスヒット）

寿命のイメージ:
  fresh（新鮮）→ stale（古いが当面は表示してよい）
  → 誰も購読していない → メモリから捨てる候補

用語メモ

staleTime … 「この写しを新鮮とみなす時間」。過ぎたら裏で取り直し候補
refetch   … 同じキーでもう一度サーバへ取りに行くこと
購読（subscribe）… キャッシュが変わったら画面に知らせてもらう登録
TypeScript
// 概念: 「キー」と「取りに行く関数」の組がキャッシュの最小単位
type QueryKey = readonly unknown[];

type Entry<T> = {
  data?: T;
  error?: unknown;
  updatedAt: number;
  subscribers: Set<() => void>;
};

// staleTime を超えたら「古い」と判定するだけの例
function isStale(entry: Entry<unknown>, staleTime: number) {
  return Date.now() - entry.updatedAt > staleTime;
}

データベースの N+1 問題との似た構造

N+1 とは、一覧を1回取ったあと、各行ごとに関連データを追加で取りに行き、合計で「1 + N 回」の問い合わせになる性能問題です（データベース章）。フロントでも、コンポーネントごとにバラバラに fetch すると、同じ「細かすぎる取り直し」が起きます。キーを共有するキャッシュは、いわば「まとめて読んで使い回す」側の設計です。一覧用キーと詳細用キーを、更新のあとどこまで無効化するかは、あらかじめ決めておく必要があります。

03

楽観更新とロールバック

▼

画面を先に進め、失敗したら元に戻す

楽観更新（Optimistic Update）とは、「サーバが成功を返す前に、うまくいった前提で手元のキャッシュと画面を先に書き換える」手法です。チェックボックスを押した瞬間に完了表示になる、といった体感の速さのためです。

サーバが失敗を返したときは、嘘のまま放置してはいけません。ロールバックとは、「更新前に取っておいたスナップショット（直前の写し）へ戻す」ことです。またはキャッシュに「古い」印を付けて（invalidate）、サーバから正しい値を取り直して再同期します。ロールバックも再取得もしない楽観更新は、障害時にブラウザだけが誤った内容を表示し続けます。

TypeScript
async function toggleDone(cache: Cache, id: string) {
  const key = ["task", id] as const;
  const prev = cache.get<Task>(key); // 直前の写しを退避（スナップショット）
  if (!prev) return;

  cache.set(key, { ...prev, done: !prev.done }); // 楽観的に先に書き換え
  try {
    await api.patch(`/tasks/${id}`, { done: !prev.done });
  } catch (e) {
    cache.set(key, prev); // 失敗したのでロールバック
    throw e;
  }
}

同時に編集されたとき（競合）

二人のユーザーが同じデータをほぼ同時に直すと、後勝ちで意図しない上書きが起き得ます。ETag や updatedAt（最終更新時刻）を更新リクエストに添え、サーバが「あなたが見ていた版ともう違う」と判断したら HTTP 409 Conflict（競合）を返す、という設計があります。409 を受けたら黙って上書きせず、invalidate して最新を取り直すのが安全です。

一覧と詳細の両方をキャッシュしている場合:
  - 詳細だけ楽観更新すると、一覧側の写しが古いまま残ることがある
  - 両方を書き換えるか、一覧キー ["tasks"] を invalidate する
04

実戦 — Query パターンの最小自作実装

▼

ライブラリ無しで「中で何をしているか」を固定する

本番アプリでは TanStack Query や SWR といったライブラリを使うことが多いです。それでも面談や設計レビューでは、「キー」「1件分のキャッシュ（Entry）」「画面からの購読」「古くなったあとの再取得」「更新（mutate）」を自分の言葉で説明できるかが問われます。以下は教育用の最小スケルトンです。本番向けに機能を削ぎ落としているので、コピーしてそのまま製品に載せる用途ではありません。

Query（クエリ）という言葉は、ここでは「あるキーに対応するデータの取得とキャッシュ管理の単位」くらいに読んでください。SQL の SELECT そのものではなく、「画面が欲しがるサーバ状態の1かたまり」に近いです。

TypeScript
type Key = string; // 本番は配列を文字列化する。ここでは簡略

type Entry<T> = {
  data?: T;
  error?: unknown;
  updatedAt: number;
  promise?: Promise<T>;
  listeners: Set<() => void>;
};

class QueryCache {
  private map = new Map<Key, Entry<unknown>>();

  get<T>(key: Key) {
    return this.map.get(key) as Entry<T> | undefined;
  }

  subscribe(key: Key, fn: () => void) {
    let e = this.map.get(key);
    if (!e) {
      e = { updatedAt: 0, listeners: new Set() };
      this.map.set(key, e);
    }
    e.listeners.add(fn);
    return () => e!.listeners.delete(fn);
  }

  private notify(key: Key) {
    this.map.get(key)?.listeners.forEach((l) => l());
  }

  setData<T>(key: Key, data: T) {
    const e = this.get<T>(key) ?? { updatedAt: 0, listeners: new Set() };
    e.data = data;
    e.error = undefined;
    e.updatedAt = Date.now();
    this.map.set(key, e as Entry<unknown>);
    this.notify(key);
  }

  async fetchQuery<T>(
    key: Key,
    fetcher: (signal: AbortSignal) => Promise<T>,
    staleTime = 30_000
  ): Promise<T> {
    const e = this.get<T>(key) ?? { updatedAt: 0, listeners: new Set() };
    this.map.set(key, e as Entry<unknown>);

    const fresh = Date.now() - e.updatedAt <= staleTime && e.data !== undefined;
    if (fresh) return e.data as T;
    if (e.promise) return e.promise as Promise<T>; // 同時に同じ取得が走ったら1本に合流

    const ac = new AbortController();
    const p = fetcher(ac.signal)
      .then((data) => {
        this.setData(key, data);
        e.promise = undefined;
        return data;
      })
      .catch((err) => {
        e.error = err;
        e.promise = undefined;
        this.notify(key);
        throw err;
      });
    e.promise = p as Promise<unknown>;
    return p;
  }

  invalidate(key: Key) {
    const e = this.get(key);
    if (!e) return;
    e.updatedAt = 0; // 即「古い」扱いにし、次の fetchQuery で再取得
    this.notify(key);
  }
}

面談で一言で言うなら

「サーバにあるデータの写しは、キー付きキャッシュに置く。画面にはまず手元の写しを出しつつ裏で取り直す（SWR）。更新は楽観的に先に進め、失敗したらロールバックする。コンポーネントはデータの持ち主ではなく、キャッシュの聞き役（購読者）である。」
