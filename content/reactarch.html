$ React / TypeScript アーキテクチャ

文法の暗記ではなく、「データがどう流れるか」「どこで型を守るか」「副作用をいつ殺すか」を、用語を一つずつ押さえながら整理する章です。Python / バックエンド / インフラの経験がある人向けです。

この章の位置づけ

React 章で文法（JSX・useState 等）を学んだあと、実案件や面談で問われる設計の理由を扱います。後続の「サーバ状態 / Query」「認証 / キャッシュ」「フロント境界テスト」章の土台になるので、ここで用語を固定しておくと読みやすくなります。

CFG（Control Flow Graph：制御フロー図）は、プログラムが「どの順でどの処理を通るか」をノードと矢印で表したものです。障害調査では「どのノードで分岐したか」を追うので、React でも更新の流れを CFG として説明できると強いです。

01

単方向データフローと CFG（Control Flow Graph）

▼

React の更新は「一方向」——双方向バインディングではない

古い UI フレームワークには双方向バインディング（画面とデータが互いに直接つながり、どちらを変えてももう一方が追従する仕組み）がありました。React は意図的にそうしません。単方向データフローとは、情報が決められた方向にしか流れない設計のことです。典型は次の流れです。

ユーザー操作（Action）→ イベントハンドラ → （必要なら）非同期 I/O → State の更新 → 画面の再描画。DOM（ブラウザ上の HTML 要素）を読んで State を「推測で」埋める逆流は避けます。逆流を許すと、どのタイミングで画面が変わったか追いにくくなり、障害時の再現グラフ（CFG 上の分岐）が爆発しやすくなります。

用語メモ

Action（アクション）
  … ユーザーの操作やシステムイベント（クリック、送信など）
Event Handler（イベントハンドラ）
  … 操作を受け取り「何をしたいか」を決める関数
State（状態）
  … 画面を描くためにコンポーネントが覚えている値
Virtual DOM / Reconciliation（仮想 DOM / 調整）
  … 前回の UI と今回の State の差分を計算し、必要な部分だけ DOM を更新する処理
Commit / Repaint（コミット / 再描画）
  … 差分を実際のブラウザ画面に反映すること
Side Effect（副作用）
  … 描画以外の仕事（fetch、タイマー、ログ出力など）

正規パス（簡略 CFG）

User Action
  → Event Handler（同期の意思決定）
  → Side Effect / Async I/O（fetch, WebSocket, timer）
  → setState / dispatch（「こうなってほしい」と宣言）
  → Virtual DOM diff（Reconciliation）
  → Commit → Browser Repaint

避けたい逆流:
  DOM を読んで State を推測で埋める
  useEffect 内で無制限に Effect を連鎖させる（観測不能ループ）

障害調査の視点

本番で「画面がおかしい」とき、追うのは「どのノードで分岐したか」です。Handler で分岐したのか、I/O 失敗後の再試行なのか、Reconciliation の結果として古い UI が残っているのか。単方向制約は、障害グラフの辺（分岐）を減らすための設計ルールです。SRE やバックエンドのログ追跡と同型の思考です。

TypeScript
// Handler は「意図」だけを書く。描画は State の写像に任せる。
function onRetry(dispatch: (a: Action) => void) {
  dispatch({ type: "logs/retry" }); // reducer / effect が I/O を担う
}
02

TypeScript による Layer 7 防衛（境界モデル）

▼

型は UI の便利機能ではない — ネットワーク境界の契約壁

OSI 参照モデルのLayer 7（アプリケーション層）は、HTTP や JSON など「アプリが意味を持つデータ」の層です。バックエンドでは FastAPI の response_model や OpenAPI が「この形の JSON だけ返す」と契約します。フロントエンドでも、API から届いた JSON をそのまま信じ込むと、壊れたデータが UI 核まで入り込みます。

TypeScript の Interface / Type（型定義）に加え、必要なら実行時の parse（検証）を境界に置くと、「不当なペイロード（想定外の JSON）をアプリの中に入れない防衛壁」になります。any はその壁に穴を開け、コンパイラのチェックを無効化する型です。

用語メモ

Interface / Type … オブジェクトの形を表す TypeScript の契約
any              … 型チェックをオフにする（防衛壁の撤去）
unknown          … 「何かは来たが形は未確定」。検証前の受け口
parse / 検証     … 実行時にフィールドの有無・型を確かめる処理
Zod 等           … スキーマ検証ライブラリの代表例
キャスト (as T)  … コンパイラへ「T だ」と伝えるだけ。検証ではない

なぜ any を避けるか

any を付けた瞬間:
- 存在しないフィールド参照がコンパイルを通る
- バックエンドの破壊的変更が「静かに」UI へ侵入する
- 障害時、型定義が「嘘のドキュメント」になる

境界の正しい受け口:
  unknown（または Zod）→ 検証 → 契約型 T
内側（描画・ドメイン）は T だけを信じる
TypeScript
// FastAPI の response_model に相当する「契約」
type Book = { id: string; title: string; updatedAt: string };

function parseBook(input: unknown): Book {
  if (!input || typeof input !== "object") throw new Error("contract");
  const o = input as Record<string, unknown>;
  if (typeof o.id !== "string" || typeof o.title !== "string") {
    throw new Error("contract");
  }
  return {
    id: o.id,
    title: o.title,
    updatedAt: typeof o.updatedAt === "string" ? o.updatedAt : "",
  };
}

運用メモ

as Book だけのキャストは検証ではありません。コンパイルは通っても実行時は壊れます。OpenAPI から型を自動生成していても、ネットワーク境界では一度 parse するのが安全です。Web/API 章の契約思考と TypeScript 章の unknown 議論と同じ線です。

03

副作用と再レンダリング最適化

▼

副作用には「寿命」がある — コンポーネントより長く生きてはいけない

useEffect は React のフックの一つで、「描画のあとに副作用を実行する」ための仕組みです。典型例は API の fetch です。fetch はネットワーク上で時間がかかるため、コンポーネントの寿命（画面に表示されている間）より長く生きることがあります。

ユーザーが画面を離れた（アンマウント：コンポーネントがツリーから外れること）あとに fetch が返ってきて setState すると、React は警告を出し、最悪はメモリリークやRace Condition（競合状態）（遅い古い応答が、新しい画面の State を上書きする現象）を起こします。

AbortController は、進行中の fetch などを「もう要らない」と打ち切るブラウザ標準の API です。useEffect のクリーンアップ（return で返す関数：コンポーネントの片付け時に実行される処理）で abort() するのが正攻法です。

用語メモ

useEffect     … 描画後に副作用を走らせる React フック
依存配列 []   … 空ならマウント時のみ / 値を入れるとその値が変わったとき再実行
アンマウント    … コンポーネントが画面から消えること
AbortController … 進行中の fetch をキャンセルする仕組み
AbortError      … 意図的に abort したとき fetch が投げるエラー（無視してよい）
再レンダリング  … State 変更などでコンポーネント関数が再度実行され UI が更新されること
TypeScript
useEffect(() => {
  const ac = new AbortController();
  (async () => {
    try {
      const res = await fetch(`/api/logs?q=${q}`, { signal: ac.signal });
      const json: unknown = await res.json();
      setLogs(parseLogList(json));
    } catch (e) {
      if ((e as { name?: string }).name === "AbortError") return;
      setError("fetch_failed");
    }
  })();
  return () => ac.abort(); // アンマウント時に通信を打ち切る
}, [q]);

State は「可能な限り狭く」——再描画コストを下げる

再レンダリングは State や親の更新のたびにコンポーネント関数が再実行されることです。State を親や Context（ツリー全体に値を配る仕組み）に無闇に上げると、関係ない子まで再描画されやすくなります。

原則:
- State は「可能な限り狭く・ローカルに」
- 親が持つ理由がない値を Context / グローバルへ上げない
- 子の再描画コスト ≈ props の参照の安定性 × 部分木の大きさ

低エントロピー（散らばりの少ない）設計:
  List は items だけ受け、行の選択状態は行コンポーネント内
  サーバ由来データは専用キャッシュ（Query 等）へ追い出し、画面 State を薄くする
  → 次章「サーバ状態 / Query」で詳述
04

実戦演習 — 型安全 fetch と loading/error 分離

▼

loading / error / data を混ぜない — 状態機械として分離する

実運用の fetch 画面では、少なくとも次の状態を区別します。loading（取得中）、error（失敗）、ready（データ表示）。これらを1つの変数に無理やり詰めると、UI 分岐が複雑になり、バグ（例: エラーなのに古い一覧が残る）が入りやすくなります。

TypeScript の判別可能ユニオン（status フィールドで分岐できる型の組み合わせ）を使うと、CFG 上のノードごとに型が絞り込まれ、描画コードが読みやすくなります。境界では unknown で JSON を受け、parseBooks で契約型に変換します。I/O 中は AbortController で打ち切り可能にします。

用語メモ

LoadState / 状態機械 … idle / loading / error / ready など取りうる状態の集合
判別可能ユニオン   … status などの共通フィールドで型を区別する書き方
parseBooks        … API JSON を unknown から Book[] 契約へ変換する境界関数
res.ok            … HTTP ステータスが 200 台かどうか（false ならエラー扱いが一般的）
TypeScript
type Book = { id: string; title: string };

type LoadState =
  | { status: "idle" | "loading" }
  | { status: "error"; message: string }
  | { status: "ready"; books: Book[] };

function parseBooks(input: unknown): Book[] {
  if (!Array.isArray(input)) throw new Error("contract");
  return input.map((row) => {
    if (!row || typeof row !== "object") throw new Error("contract");
    const o = row as Record<string, unknown>;
    if (typeof o.id !== "string" || typeof o.title !== "string") {
      throw new Error("contract");
    }
    return { id: o.id, title: o.title };
  });
}

function BookPanel() {
  const [state, setState] = useState<LoadState>({ status: "idle" });

  useEffect(() => {
    const ac = new AbortController();
    setState({ status: "loading" });
    (async () => {
      try {
        const res = await fetch("/api/books", { signal: ac.signal });
        if (!res.ok) throw new Error(`http_${res.status}`);
        const books = parseBooks(await res.json());
        setState({ status: "ready", books });
      } catch (e) {
        if ((e as { name?: string }).name === "AbortError") return;
        setState({
          status: "error",
          message: e instanceof Error ? e.message : "unknown",
        });
      }
    })();
    return () => ac.abort();
  }, []);

  if (state.status === "loading" || state.status === "idle") {
    return <p className="term">loading…</p>;
  }
  if (state.status === "error") {
    return <p className="term err">ERR {state.message}</p>;
  }
  return (
    <ul className="term">
      {state.books.map((b) => (
        <li key={b.id}>{b.title}</li>
      ))}
    </ul>
  );
}

面談で一言で言うなら

「UI は契約型の写像。I/O は Abort 可能な副作用。State は局所化し、loading / error / data を混ぜない。サーバ由来の一覧は次章以降、Query キャッシュへ追い出す。」
