ログイン状態（セッション）の寿命と、前章のサーバ状態キャッシュの寿命をそろえる章です。「ログイン情報をどこに置くか」「ログアウトや期限切れのあと、古いデータを残さないか」「画面でボタンを隠すだけで守れているか」を、用語を一つずつ押さえながら整理します。

この章の位置づけ

「サーバ状態 / Query」章の続きです。よくある事故は、ログアウトしたあと、またはログインの有効期限が切れたあとにも、ブラウザのメモリ上に前のユーザーのタスク一覧などが残っていることです。セキュリティ章や Web/API 章で出た用語を、フロントエンドの運用手順に接続します。

01

Cookie セッション vs Bearer — 保管場所と攻撃面

▼

ログイン証明の「置き場」を選ぶと、狙われ方も決まる

ログインしたことをサーバに証明するための文字列を、ここではまとめてトークン（通行证のようなもの）と呼びます。JWT（JSON Web Token）は、そのトークンのよくある形式の一つで、中にユーザー ID などを載せた署名付きの文字列です。Bearer（ベアラ）は HTTP の Authorization: Bearer <トークン> のように「このトークンを持っている者が本人である」と伝える送り方の名前です。

ブラウザの localStorage（ドメインごとに文字列を保存できる領域）に JWT を置くと、JavaScript からいつでも読めます。その結果、XSS（Cross-Site Scripting：悪意のあるスクリプトをページに紛れ込ませる攻撃）が一度成功すると、攻撃者のスクリプトがトークンを読み取り、Bearer として API を呼べてしまいます。「XSS 一本で通行证ごと盗まれる」とはこの意味です。

一方、Cookie（ブラウザが自動でサーバへ添える小さなデータ）にセッション情報を載せ、HttpOnly 属性を付けると、JavaScript からはその Cookie を読めません。XSS が起きても「JS がトークンをコピーして外へ送る」経路は塞ぎやすくなります。あわせて Secure（HTTPS のときだけ送る）や SameSite（どのサイトからのリクエストに Cookie を付けるか制限する）もよく使います。

ただし Cookie 方式は別の攻撃 CSRF（Cross-Site Request Forgery：別サイトから、ログイン済みブラウザに意図しないリクエストを送らせる攻撃）への対策が必要になります。対策の例は、フォームに独自の CSRF トークンを載せる、SameSite を厳しくする、などです。

どちらの方式が「常に正解」ではありません。選んだ保管場所ごとに、対応する防御を必ず載せる、というのが設計の原則です。

用語メモ（このレッスンの単語帳）

トークン     … ログイン済みであることを示す文字列（通行证）
JWT         … よく使われるトークン形式の一種
Bearer      … Authorization ヘッダでトークンを渡す方式の名前
localStorage … JS から読めるブラウザ内の保存領域
XSS         … ページに悪意あるスクリプトを仕込む攻撃
Cookie      … ブラウザがリクエストに自動添付する小さなデータ
HttpOnly    … Cookie を JS から読めなくする属性
Secure      … HTTPS のときだけ Cookie を送る属性
SameSite    … 他サイト経由のリクエストに Cookie を付けるかを制限
CSRF        … 他サイトから「本人のブラウザ」に不正操作をさせる攻撃
セッション   … 「いま誰としてログインしているか」のサーバ側の文脈

方式ごとの得失（面談用の整理）

Bearer を localStorage やメモリに置く場合:
  良い点: SPA（単一ページアプリ）から付け替えやすい
  悪い点: XSS が成功するとトークンがすぐ盗まれる
  悪い点: タブ間の共有や「どこまで残すか」が雑になりやすい

HttpOnly Cookie でセッションを持つ場合:
  良い点: XSS でも JS がトークン文字列を直接読めない
  悪い点: CSRF 対策（トークンや SameSite など）が必須
  悪い点: 別ドメインの API を叩くとき credentials 設計が要る
           （Cookie を送るかどうかの明示）

実務でよくある折衷:
  短命の access トークンはメモリだけに置き、
  長めの refresh 用は HttpOnly Cookie に置く。
  → 延長（refresh）だけ Cookie、普段の API は短命トークン。

障害・漏洩調査の視点

インシデント対応で最初に確認するのは「トークンはどこに置いていたか」です。置き場がコードベース全体でバラバラだと、「どこまで漏洩したか」の見積もりができません。保管方針はチームで一文に固定しておく価値があります。

02

401/403 と Query キャッシュの clear

▼

ログインが終わった瞬間＝キャッシュも終わりにする

HTTP のステータスコード 401 Unauthorized は、ざっくり言うと「あなたが誰か分からない／ログインが無効」という応答です。明示的なログアウトも同様に、「もうこのユーザーとしては操作しない」状態です。

この直後に、前章の Query キャッシュ（サーバから取ったデータの写しをキーごとに覚えておく領域）を残したままだと、次にログインした別ユーザーや、同じ端末の別セッションに、前の人の一覧などが見える危険があります。キーを1つずつ invalidate（古い印）するだけでは漏れやすいので、原則は clear() でキャッシュを全部捨てるか、キーの先頭にユーザー ID を付けて「そのユーザー分をまとめて捨てる」設計にします。

用語メモ

401 … 未ログイン／セッション無効。再ログインが必要になりやすい
403 … ログイン自体はできているが、その操作は許可されない（権限不足）
clear() … キャッシュ全体を空にする
invalidate … 特定キーだけ「古い」にして取り直し候補にする
TypeScript
// API 呼び出しを包むラッパの概念コード
async function apiFetch(input: RequestInfo, init?: RequestInit) {
  const res = await fetch(input, { credentials: "include", ...init });
  if (res.status === 401) {
    authStore.setSession(null); // 「いま誰か」を忘れる
    queryCache.clear();         // 前ユーザーの写しを残さない
    navigateToLogin();          // ログイン画面へ
    throw new Error("unauthorized");
  }
  if (res.status === 403) {
    // ログインは有効だが権限不足 — 通常はキャッシュ全消ししない
    throw new Error("forbidden");
  }
  return res;
}

function logout() {
  authStore.setSession(null);
  queryCache.clear();
  // あわせてサーバ側のセッション破棄 API も呼ぶ
}

401 と 403 を同じ処理にしない

401 Unauthorized
  → 「誰かが分からない／ログイン無効」
  → 再ログインへ誘導 + キャッシュ clear

403 Forbidden
  → 「誰かは分かるが、その操作は禁止」
  → 権限エラーの表示など
  → ここで clear すると、使えるデータまで消えて UX が壊れる

credentials: "include" は、Cookie をリクエストに含めて送る指定です。Cookie セッション方式ではこれが無いとログイン状態がサーバに伝わりません。

03

認可境界 — UI の role 分岐は装飾

▼

画面から隠すことと、実際に守れていることは別

認証（Authentication）は「あなたは誰か」を確かめること、認可（Authorization）は「その誰かが、その操作をしてよいか」を確かめることです。よく混同されます。

React で {role === "admin" && <AdminPanel />} のように管理者メニューを出さないのは、見た目・操作感のための最適化（UX）であり、認可そのものではありません。ブラウザの開発者ツールや、API への直接リクエストで突破できます。本当の認可はサーバ側で、所有者かどうか・権限があるかを毎回検証します。フロントの役割は「一般ユーザーには見せない」までです。

IDOR をフロントのリンク非表示だけで防がない

IDOR（Insecure Direct Object Reference）は、URL や ID を書き換えて、本来見てはいけない他人のリソースに直接アクセスできてしまう一类の欠陥です。

BAD（不十分）:
  「自分の一覧に無い /tasks/123 はリンクしない」
  → 攻撃者は /tasks/124 を手打ちやツールで GET する

GOOD:
  API が「このリソースの所有者 === 今のログインユーザーか」を検証する
  フロントは 403 や 404 を正しく表示するだけ

/me（「いまの自分」を返す API）の役割:
  表示名や role（役割）のヒントをフロントに渡す
  それでも、更新・削除など各操作の許可はサーバが再度確かめる

キャッシュキーに userId を入れる理由

同じブラウザでユーザーを切り替える可能性があるなら、キーを ["tasks", userId] のようにユーザー単位で分けると、別人の写しが同じ枠に混ざりにくくなります。これは clear を忘れたときの保険になります。ただし保険があるからといって、ログアウト時の clear 自体を省略してよい理由にはなりません。

04

実戦 — authStore + cache.clear + /me

▼

最小の運用骨格をコードで見る

セッション（「いま誰として操作しているか」）はクライアント状態です。一方 /api/me が返すプロフィール（名前や role）はサーバ状態で、前章のキャッシュに載せてよいデータの一例です。ログアウトでは、セッションを消し、キャッシュも消すを同じタイミングで行います。

下の parseMe は、API の JSON を信じ込まず、形を確認してから型の付いた値にする例です（TypeScript の境界防衛。CFG/UI防衛章や TypeScript 章と同型の発想です）。

TypeScript
type Session = { userId: string; role: "user" | "admin" };

type Me = { id: string; name: string; role: Session["role"] };

function parseMe(input: unknown): Me {
  if (!input || typeof input !== "object") throw new Error("contract");
  const o = input as Record<string, unknown>;
  if (typeof o.id !== "string" || typeof o.name !== "string") {
    throw new Error("contract");
  }
  if (o.role !== "user" && o.role !== "admin") throw new Error("contract");
  return { id: o.id, name: o.name, role: o.role };
}

// 概念的な authStore（実装は Context や zustand などでもよい）
const authStore = {
  session: null as Session | null,
  setSession(s: Session | null) {
    this.session = s;
  },
};

async function bootstrapSession(cache: { clear: () => void; fetchQuery: Function }) {
  try {
    const res = await fetch("/api/me", { credentials: "include" });
    if (res.status === 401) {
      authStore.setSession(null);
      cache.clear();
      return null;
    }
    if (!res.ok) throw new Error(`http_${res.status}`);
    const me = parseMe(await res.json());
    authStore.setSession({ userId: me.id, role: me.role });
    // /me の結果もサーバ状態としてキャッシュしてよい
    await cache.fetchQuery(["me", me.id], async () => me);
    return me;
  } catch {
    authStore.setSession(null);
    cache.clear();
    return null;
  }
}

function logout(cache: { clear: () => void }) {
  void fetch("/api/logout", { method: "POST", credentials: "include" });
  authStore.setSession(null);
  cache.clear();
}

面談で一言で言うなら

「トークンをどこに置くかで、XSS や CSRF のどちらを主に防ぐかが変わる。401 やログアウトでは Query キャッシュを空にする。画面の role 分岐は見せ方の話で、許可するかどうかの判定は API 側が真実。」
