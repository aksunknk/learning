$ 認証 / キャッシュ

セッションの寿命と Query キャッシュの寿命を同期させる。トークンの置き場・401 処理・認可の真実は API 側。

SCOPE

serverstate 章の続き。ログアウト／トークン失効後も古いサーバ状態の写しが残るのが典型事故。Security・Web/API の用語をフロント運用に接続する。

01

Cookie セッション vs Bearer — 保管場所と攻撃面

▼

トークンの置き場 = 攻撃面の選択

localStorage に JWT を置くと、XSS 一本で Bearer ごと盗まれる。HttpOnly + Secure + SameSite の Cookie セッションは JS から読めない一方、CSRF 対策（トークン／SameSite）が必須になる。どちらかが「常に正しい」のではなく、選んだ保管場所に対応する防御を必ず載せる。

対応表（面談用）

Bearer in localStorage / memory:
  + SPA から付け替えやすい
  - XSS → 即トークン漏洩
  - タブ間共有・永続化の設計が雑になりがち

HttpOnly Cookie セッション:
  + XSS でも JS がトークンを読めない
  - CSRF（POST 等）対策が必須
  - クロスオリジンでは credentials 設計が要る

実務の折衷（よくある）:
  短期 access（memory）+ 長期 refresh（HttpOnly Cookie）
  → refresh 経路だけ Cookie、API 呼び出しは短命トークン

SRE 視点

インシデントで最初に聞くのは「トークンはどこにいたか」。置き場が決まっていないコードベースは、漏洩範囲の見積もりができない。

02

401/403 と Query キャッシュの clear

▼

セッション終了 = キャッシュの死亡時刻

401（未認証）や明示ログアウトの直後に Query キャッシュを残すと、次のユーザー（または同一端末の別セッション）に前ユーザーの写しが見える。invalidate 個別キーでは足りないことが多い。原則は clear()（全破棄）またはユーザー ID をキー接頭辞にして丸ごと捨てる。

TypeScript
// fetch ラッパの概念
async function apiFetch(input: RequestInfo, init?: RequestInit) {
  const res = await fetch(input, { credentials: "include", ...init });
  if (res.status === 401) {
    authStore.setSession(null);
    queryCache.clear(); // 前ユーザーのサーバ状態を残さない
    navigateToLogin();
    throw new Error("unauthorized");
  }
  if (res.status === 403) {
    // 認証は有効だが権限不足 — キャッシュ全消しは通常不要
    throw new Error("forbidden");
  }
  return res;
}

function logout() {
  authStore.setSession(null);
  queryCache.clear();
  // サーバ側セッション破棄 API も呼ぶ
}

401 と 403 を混ぜない

401 Unauthorized … 誰かが分からない／セッション無効 → 再ログイン + clear
403 Forbidden   … 誰かは分かるが許可されない → 権限 UI / エラー表示
                  （誤って clear すると UX が壊れる）
03

認可境界 — UI の role 分岐は装飾

▼

隠すこと ≠ 守れていること

{role === "admin" && <AdminPanel />} は UX 最適化であり認可ではない。DevTools や直接 API 呼び出しで突破される。真実の認可はサーバ（所有者チェック・権限）。フロントは「見えないようにする」だけを担当する。

IDOR をフロントだけで防がない

BAD:
  /tasks/123 を「自分の一覧に無い ID はリンクしない」
  → 攻撃者は 124, 125 を直接 GET する

GOOD:
  API が resource.owner_id === session.user_id を検証
  フロントは 403/404 を正しく表示するだけ

/me の役割:
  表示名や role のヒントを返す
  それでも各 mutation の認可はサーバが再検証する

キャッシュキーに userId を入れる理由

同一ブラウザでユーザー切替があり得るなら、キーを ["tasks", userId] のようにスコープする。clear 忘れの保険になるが、clear 自体を省略する理由にはならない。

04

実戦 — authStore + cache.clear + /me

▼

最小運用骨格

セッションはクライアント状態（誰として操作しているか）。/me のプロフィールはサーバ状態。ログアウトは両方を同時に殺す。

TypeScript
type Session = { userId: string; role: "user" | "admin" };

type Me = { id: string; name: string; role: Session["role"] };

function parseMe(input: unknown): Me {
  if (!input || typeof input !== "object") throw new Error("contract");
  const o = input as Record<string, unknown>;
  if (typeof o.id !== "string" || typeof o.name !== "string") {
    throw new Error("contract");
  }
  if (o.role !== "user" && o.role !== "admin") throw new Error("contract");
  return { id: o.id, name: o.name, role: o.role };
}

// 概念的 authStore（実装は context / zustand 等）
const authStore = {
  session: null as Session | null,
  setSession(s: Session | null) {
    this.session = s;
  },
};

async function bootstrapSession(cache: { clear: () => void; fetchQuery: Function }) {
  try {
    const res = await fetch("/api/me", { credentials: "include" });
    if (res.status === 401) {
      authStore.setSession(null);
      cache.clear();
      return null;
    }
    if (!res.ok) throw new Error(`http_${res.status}`);
    const me = parseMe(await res.json());
    authStore.setSession({ userId: me.id, role: me.role });
    // /me 自体もサーバ状態としてキャッシュしてよい
    await cache.fetchQuery(["me", me.id], async () => me);
    return me;
  } catch {
    authStore.setSession(null);
    cache.clear();
    return null;
  }
}

function logout(cache: { clear: () => void }) {
  void fetch("/api/logout", { method: "POST", credentials: "include" });
  authStore.setSession(null);
  cache.clear();
}

面談で一言で言うなら

「トークンの置き場で攻撃面が決まる。401 とログアウトではキャッシュを殺す。role 分岐は UX、認可は API。」
