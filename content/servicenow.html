01

ServiceNowの正体 — なぜ「クラウド上の巨大Django Admin」なのか

▼

💡 🎯 ServiceNowの本質は「PaaS型の超巨大RDB + ワークフロー基盤」

ServiceNow（SN）は、単なるITヘルプデスクのSaaSではありません。Python（Django/FastAPI）などでWebアプリを自作した経験があるなら、SNを「超高機能なDjango Admin画面が最初から乗っている、単一の巨大リレーショナルデータベース（MariaDBベース）」と考えると最も実態に近いです。

通常のSaaSがテナント間でDBを共有するのに対し、SNは「マルチインスタンス」アーキテクチャを採用しています。顧客ごとに独立したDBとアプリケーションノードが割り当てられるため、他の顧客の負荷に引きずられず、極めてセキュアで高度なカスタマイズが可能です。

📊 既存のWeb開発との対応表

概念一般的なWeb開発ServiceNowでの呼称 / 機能

レコード/行RowRecord

💼 Tips：実務・試験で遭遇する勘所と落とし穴

ServiceNowの開発は「ゼロからコードを書く」のではなく、「すでに完成している巨大なERP/CRMシステムの振る舞いを、設定とスクリプト（JavaScript）で上書き（Override）していく」作業です。そのため、既存のアーキテクチャ（テーブルや標準スクリプト）に逆らってフルスクラッチのUIを作ろうとすると、アップデート時の保守コストが跳ね上がり破綻します。「プラットフォームのレールに乗る（Stay Out-of-the-Box）」ことがシニアSNエンジニアの鉄則です。
02

データ層：テーブルと継承モデル（Task と Incident）

▼

💡 🎯 ServiceNowの心臓部は「Task [task]」テーブル

ServiceNowの最も強力な機能の一つが「テーブルの継承（Table Extension）」です。RDBにおいて、共通の属性（「アサイン先」「ステータス」「作成日」など）を持つテーブルを設計する際、SNでは基底テーブルである Task [task] テーブルを継承して新しいテーブルを作成します。

SQL vs ServiceNowのテーブル関係 
-- もしゼロからSQLでIncidentテーブルを作るなら：
CREATE TABLE incident (
    id VARCHAR(32) PRIMARY KEY, -- ServiceNowでは sys_id (32桁のGUID)
    short_description VARCHAR(255),
    state INT,
    assigned_to VARCHAR(32) REFERENCES sys_user(id)
    -- ...
);

/* ServiceNowの継承モデルの概念：
 * Incident (インシデント), Problem (問題), Change Request (変更要求) は
 * 全て Task (task) テーブルを「継承」している。
 * 
 * [task] テーブル (親)
 *   ├── state, assigned_to, short_description, sys_created_on などを保持
 *   │
 *   ├── [incident] テーブル (子)
 *   │     └── caller_id (起票者) など、インシデント特有のフィールドを追加
 *   │
 *   └── [change_request] テーブル (子)
 *         └── risk (リスクレベル) など、変更要求特有のフィールドを追加
 */

🔑 sys_id と カスタムプレフィックス

ServiceNow内のすべてのレコードは、必ず sys_id という32文字のグローバル一意識別子（GUID）を持ちます。これは絶対に一意であり、外部キー（Reference）として他のテーブルから参照される際のキーになります。

また、開発者が独自に追加したテーブルやフィールドには、必ず u_ (グローバルスコープ) または x_ (Scoped App) というプレフィックスが自動付与されます（例：u_custom_table）。これにより、将来のシステムアップデートで同名の標準テーブルが追加されても衝突しません。

💼 Tips：実務・試験で遭遇する勘所と落とし穴

実務では「Incident一覧を出して」と言われたら incident テーブルをクエリしますが、「自分にアサインされている全ての作業（IncidentもTaskもChangeも）を出して」と言われたら、親である task テーブルに対してクエリ（assigned_to=自分のsys_id）を投げます。継承の概念を理解していないと、テーブルごとに個別クエリを投げる非効率な設計になってしまいます。
03

CMDBと構成アイテム（CI）

▼

💡 🎯 CMDBは「ITインフラの設計図（デジタルツイン）」

CMDB（Configuration Management Database：構成管理データベース）は、企業内のサーバー、PC、ソフトウェア、ネットワーク機器、さらには「メールサービス」といった無形のサービスまで、IT資産のすべてを構成アイテム（CI：Configuration Item）として格納する巨大なツリー構造のテーブル群です。

🌲 cmdb_ci のクラス階層

CMDBも強力な継承モデルを持っています。頂点にあるのが cmdb_ci テーブルです。

  • cmdb_ci (すべてのCIの親)
    • cmdb_ci_hardware (ハードウェア)
      • cmdb_ci_computer (コンピュータ)
        • cmdb_ci_server (サーバー / Windows, Linux等)
    • cmdb_ci_appl (アプリケーション)

さらに、これらのCI間には関係性（Relationship）が定義されます。（例：「Linux Server A」は「Oracle DB B」を Runs on（上で動かしている））。

💼 Tips：実務・試験で遭遇する勘所と落とし穴

Incident（障害）が発生した際、影響範囲を特定するために「どのCIで障害が起きたのか」をレコードに紐づけます（incident.cmdb_ci フィールド）。CMDBの関係性を辿る（Dependency Views）ことで、「このDBサーバーが落ちたら、上のWebサービス、ひいては社内の稟議システム全体が停止する」という影響を瞬時に可視化できるのが、SNを単なるチケット管理ツールから「エンタープライズIT基盤」に押し上げている最大の理由です。
04

画面層：List・Form・Viewの仕組み

▼

💡 🎯 スキーマ駆動のUI自動生成

ReactやVueで画面を作る場合、HTML/CSSとデータバインディングを自作しますが、SNの基本UI（UI16 / Next Experience）では、テーブルのスキーマ（カラム定義）を作成した瞬間に、List（一覧画面）とForm（詳細・編集画面）が自動生成されます。

🎨 View（ビュー）による画面の切り替え

同じ incident テーブルのデータでも、「一般ユーザーが見る画面」と「システム管理者が調査する画面」では、表示すべきフィールドが異なります。SNではこれをView（ビュー）という概念で解決します。

  • Default View: 担当者向けのフル機能フォーム。
  • Self Service View (ess): エンドユーザー向けのシンプルなフォーム（専門用語や内部ステータスを隠す）。
  • Mobile View: モバイルアプリ用のコンパクトな表示。

💼 Tips：実務・試験で遭遇する勘所と落とし穴

「このフィールドを画面の右上に配置して、背景を赤くして…」といったピクセルパーフェクトなUI要件は、標準のForm/Listでは実現困難（あるいは多大なDOMハックが必要で負債になる）です。そうしたBtoCのような柔軟なUIが必要な場合は、標準画面をいじるのではなく、Service Portal (AngularJSベース) や UI Builder (Next Experience) を用いて専用のポータル画面を構築するのがアーキテクチャの正解です。
05

クライアントサイド制御：Client Script と UI Policy

▼

💡 🎯 ブラウザ側で動くJS ＋ ノーコード制御

ユーザーがForm画面を開いた時や、入力フィールドの値を変更した瞬間に「動的」に画面を制御（フィールドを隠す、必須入力にする、アラートを出す等）するための仕組みがクライアントサイド制御です。

Client Script (JavaScript) の例 
// onChange Client Script
// 「Category」フィールドが "Software" に変更された時だけ動くスクリプト

function onChange(control, oldValue, newValue, isLoading, isTemplate) {
    if (isLoading || newValue === '') {
        return;
    }

    if (newValue == 'software') {
        g_form.setDisplay('subcategory', true);
        g_form.setMandatory('subcategory', true);
        g_form.addInfoMessage('ソフトウェアの問題ですね。OSの種類を忘れずに記載してください。');
    } else {
        g_form.setMandatory('subcategory', false);
        g_form.setDisplay('subcategory', false);
    }
}

⚖️ UI Policy vs Client Script

上記のJSと全く同じこと（フィールドの表示/非表示、必須化、読取専用化）は、コードを書かずにUI Policy（ノーコード設定）でも実現可能です。

ルール： 「UI Policyで実現できることは、絶対にClient Scriptで書かない」

UI Policyはブラウザ上で高速に評価され、保守も容易（一覧で条件が見える）です。Client Scriptは、UI Policyでは不可能な複雑な計算、外部API(GlideAjax)の呼び出し、ダイアログ(GlideDialogWindow)の表示などに限定して使用します。

⚠️ 実行順序の罠

画面ロード時の実行順序は Client Script (onLoad) → UI Policy の順です。Client Scriptで一生懸命フィールドを表示させても、その直後にUI Policyの条件に合致して非表示に上書きされる、というバグが初学者の「あるある」です。
06

サーバーサイド制御①：Business Rule

▼

💡 🎯 データベースのTriggerに相当するサーバー処理

レコードがデータベースに保存される「直前（Before）」や「直後（After）」に発火するサーバースクリプトがBusiness Rule (BR)です。ユーザーが画面から保存ボタンを押した時だけでなく、外部からのREST API経由の更新や、インポート処理など、すべてのDB更新ルートで確実に実行されるため、データ整合性を担保する最強の番人となります。

Before Update Business Rule の例 
(function executeRule(current, previous /*null when async*/) {
    if (current.close_notes.nil()) {
        gs.addErrorMessage('インシデントを解決済みとするには、解決手順(Close Notes)の入力が必須です。');
        current.setAbortAction(true);
    }
})(current, previous);

⏱️ Business Rule の 4つの実行タイミング

  • Before: DBに書き込まれる直前。バリデーション（データチェック）や、フィールドの自動計算（例：A+Bの値をCにセットして保存）に最適。
  • After: DBに書き込まれた直後。他テーブルのレコードを連動して更新する場合（例：Incidentが作られたら、紐づくProblemの件数をカウントアップする）に使用。
  • Async: Afterと同じくDB保存後だが、非同期（バックグラウンドワーカー）で実行。ユーザーの画面応答を待たせないため、外部API連携など時間のかかる処理に必須。
  • Display: ユーザーがフォームを「開いた時（DBからReadした直後）」。Client Script（ブラウザ）にサーバー側の事前データを渡す（g_scratchpad変数）ために使う特殊なBR。

💼 Tips：実務・試験で遭遇する勘所と落とし穴

Before BRの中で current.update() を呼ぶのは最悪のアンチパターン（無限ループの引き金）です。Beforeは「これから自動でDBにUpdateされる直前のオブジェクトを操作している」状態なので、変数に値を代入する（current.u_my_field = 'x';）だけで、その後の自動Update処理で勝手にDBに保存されます。
07

サーバーサイド制御②：GlideRecord と Script Include

▼

💡 🎯 ServiceNow専用のORM：GlideRecord

ServiceNowでデータベースにクエリを投げたりCRUD操作を行うためのコアAPIがGlideRecordです。SQLを直接書くことは許されておらず、すべてこのオブジェクト指向ラッパーを経由します。

GlideRecordによるクエリと更新 
var grInc = new GlideRecord('incident');
grInc.addQuery('priority', 1);
grInc.addQuery('active', true);
grInc.query();

while (grInc.next()) {
    gs.info('Critical Incident Found: ' + grInc.number);
    grInc.work_notes = 'システム管理者による一斉パトロールチェック済み';
    grInc.update();
}

🧩 Script Include（共通クラスライブラリ）

Business Ruleの中に長々としたビジネスロジックを書くと、他のルールから再利用できずスパゲティ化します。そこで、再利用可能な関数群やクラス定義を「Script Include」として切り出し、Business Ruleからはそれを呼び出す設計にするのがベストプラクティスです。

💼 Tips：実務・試験で遭遇する勘所と落とし穴

GlideRecordで next() ループを回しながら update() や deleteRecord() を連続で叩くと、巨大なテーブルではパフォーマンスが死にます。条件に合致するものを一括更新したい場合は、updateMultiple() を使いましょう。SQLの UPDATE table SET x=y WHERE z に相当し、RDBレイヤーで一括処理されるため劇的に高速です。

クライアント・サーバー非同期通信：GlideAjax

▼

💡 🎯 画面を固めずにサーバー処理を呼び出す

「画面（Client Script）でユーザーが入力したIDをもとに、サーバー（DB）を参照してユーザーの部署名を取得し、画面に自動セットしたい」── こうしたフロント⇔バックエンド通信の王道がGlideAjaxです。

GlideAjaxの実装パターン（Client → Script Include） 
// ==============================================
// 1. サーバー側: Script Include (必ず "Client callable" にチェックを入れる)
// ==============================================
var UserAjaxUtils = Class.create();
UserAjaxUtils.prototype = Object.extendsObject(AbstractAjaxProcessor, {
    getDepartment: function() {
        var userId = this.getParameter('sysparm_user_id');
        var gr = new GlideRecord('sys_user');
        if (gr.get(userId)) {
            return gr.department.getDisplayValue();
        }
        return '';
    },
    type: 'UserAjaxUtils'
});

// ==============================================
// 2. クライアント側: Client Script (onChange等)
// ==============================================
function onChange(control, oldValue, newValue, isLoading, isTemplate) {
    if (isLoading || newValue === '') return;
    var ga = new GlideAjax('UserAjaxUtils');
    ga.addParam('sysparm_name', 'getDepartment');
    ga.addParam('sysparm_user_id', newValue);
    
    ga.getXMLAnswer(function(answer) {
        if (answer) {
            g_form.setValue('u_department_name', answer);
        }
    });
}

⚠️ getReference()の罠

クライアントスクリプトには g_form.getReference('caller_id') という、指定した参照先のレコード情報を丸ごと取ってくる便利関数があります。しかし、これはバックグラウンドで不要なカラム（数十〜数百個）まで全てDBから引っ張ってくる（SELECT * 状態）ため、通信量が肥大化しパフォーマンス劣化の温床になります。必要な1〜2カラムだけを GlideAjax でピンポイントに取得するのがシニアエンジニアの流儀です。
09

自動化層：Flow Designer

▼

💡 🎯 スクリプトから「ノーコード・ワークフロー」へのパラダイムシフト

従来、複雑な承認プロセスやタスクの自動生成はBusiness Rule等でJavaScriptを書き殴って実装されていました。これを可視化されたノーコードGUIで定義できるようにした最新エンジンが Flow Designer です。

🔄 Flow Designer の基本構造

  • Trigger (トリガー): フローが発火する条件。（例：「IncidentテーブルにレコードがInsertされた時」）
  • Action (アクション): 実行する処理。（例：「レコードを作成」「承認要求（Ask for Approval）」「メール送信」）
  • Data Pill (データピル): 画面右側のペインから、前段のアクションで取得したデータをドラッグ＆ドロップで後段のアクションの引数として渡す仕組み。

💼 Tips：実務・試験で遭遇する勘所と落とし穴

Flow Designerを使う最大のメリットは「状態（State）の待機」が極めて簡単に書けることです。例えば「上長の承認を待つ」というActionを配置すると、フローはそこで一旦スリープ状態になり、誰かが承認ボタンを押した瞬間に再開します。これをスクリプト（BR等）で実装しようとすると、状態をDBフラグで管理してバッチで監視する…といった非常に泥臭くバグの出やすい実装になります。「待機・承認・通知」が絡むロジックは迷わずFlow Designerを選択しましょう。
10

外部連携層：Integration Hub と REST API

▼

💡 🎯 ServiceNowを「Hub」として企業システムを連結する

ServiceNowは単体で完結せず、企業のあらゆるSaaS（Slack, Teams, Salesforce, SAP, AWS, ADなど）のオーケストレーターとして機能します。これをノーコードで実現する強力な拡張機能が Integration Hub (IH) です。

Scripted REST API ── 外部からSNを叩かせる独自エンドポイント 
(function process(/*RESTAPIRequest*/ request, /*RESTAPIResponse*/ response) {
    var body = request.body.data;
    var slackMsg = body.text;
    var slackUser = body.user_name;
    
    var grInc = new GlideRecord('incident');
    grInc.initialize();
    grInc.short_description = 'Slack発: ' + slackMsg;
    grInc.caller_id.setDisplayValue(slackUser);
    var newSysId = grInc.insert();
    
    response.setStatus(201);
    response.setBody({
        "status": "success",
        "incident_number": grInc.number,
        "sys_id": newSysId
    });
})(request, response);

🔌 Inbound と Outbound の使い分け

  • Outbound (SN → 外部へ):
    SNのレコードが更新されたらSlackに通知する等。Flow Designer + Integration Hubの「Spoke (各SaaS用プラグイン)」を使うのがモダンなアプローチ。
  • Inbound (外部 → SNへ):
    外部システムがSNのデータを作成・取得する。標準の Table APIがデフォルトで開いているため基本はそちらを利用。標準APIで要件を満たせない場合のみ Scripted REST API を作成する。

💼 Tips：実務・試験で遭遇する勘所と落とし穴

外部連携の実装で最も危険なのは「同期処理で外部APIを叩く」ことです。Business Rule (Before/After) の中で外部APIを呼ぶと、外部の応答が遅い（タイムアウト）場合に、ユーザーの画面（Saveボタンを押した直後）も数秒〜数十秒フリーズします。外部通信は必ず「Async Business Rule」や「Flow Designer」の非同期ワーカーに投げさせるのがアーキテクチャの絶対条件です。
