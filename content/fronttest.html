$ フロント境界テスト

Query・認証で設計した「状態の分かれ道」を、テストで固定する章です。ライブラリ名の暗記より、何をモックし、画面に何が見えれば合格かを言葉にします。

この章の位置づけ

直前までのフロント編（CFG → Query → 認証）は「どう設計するか」でした。テスト設計章には Playwright や RTL の概要がありますが、サーバ状態の loading/error、楽観更新の失敗、ログアウト後のキャッシュ破棄を具体的にどう断言するかは未接続です。この章がその橋です。

RTL（React Testing Library）は、ボタンの有無やテキストなど「ユーザーが画面で見ること・操作すること」を中心にコンポーネントを検証するテスト用ライブラリです。MSW（Mock Service Worker）は、テスト中の fetch を横取りし、偽の API 応答を返す仕組みです。本物のサーバを立てなくても、成功や 401 を意図どおり再現できます。

01

なぜ loading / error / empty を分けてテストするか

▼

画面は「状態機械」——各ノードをユーザー視点で固定する

サーバ状態を扱う画面は、だいたい次の状態を行き来します。loading（読み込み中）、error（失敗してメッセージを出す）、empty（成功したが件数がゼロ）、ready（一覧や詳細が見える）。CFG / Query 章で「loading と error を同じ変数に詰め込まない」と言ったのは、UI 分岐がこのノードごとに分かれるからです。

テストも同様に分けます。「データがあるとき一覧が出る」だけ通しても、失敗時にスピナーが永遠に回り続けるバグは検知できません。アサーション（assertion：期待どおりかを確かめる文）は、実装の内部変数名ではなく、getByText("読み込み中") や getByRole("alert") のように、ユーザーが知覚する結果に書きます。これが RTL の流儀です。

用語メモ

RTL (React Testing Library)
  … 画面に出るもの・操作を中心にコンポーネントをテストするライブラリ
アサーション
  … 「こうなっていてほしい」をコードで確認すること（expect など）
状態機械
  … 取りうる状態と、状態間の遷移を明示したモデル
E2E (End-to-End)
  … ブラウザごとアプリ全体を動かす重いテスト（Playwright 等）
  … 本章の RTL + MSW は「境界の薄い層」。ログイン〜決済の一本道は E2E に残す

最低限そろえるケース表

loading → 「読み込み中」相当が見える / 一覧はまだ無い
error   → エラー文言が見える / 一覧は出さない
empty   → 「0件」や空の案内が見える
ready   → タスク名など実データが見える

やってはいけない:
  実装の state.status === "loading" を直接覗くだけ
  → リファクタで壊れ、ユーザー体験とずれる
02

MSW で成功・401・500 を固定する

▼

ネットワーク境界を「台本」にする

コンポーネントテストで本物のバックエンドに依存すると、サーバの起動・データの初期状態・ネットワーク揺らぎでテストが赤くなったり緑になったりします（フレーク）。モックとは、本物の代わりに用意する偽の応答です。MSW はブラウザ／Node のネットワーク層に近いところで fetch を横取りするため、アプリコードは本番と同じ fetch("/api/tasks") のまま、応答だけ台本に差し替えられます。

認証章で扱った 401（未ログイン）、サーバ障害の 500、成功の 200 をケースごとに切り替えると、「成功パスだけ通るテスト」から卒業できます。

用語メモ

MSW (Mock Service Worker)
  … fetch を横取りして偽レスポンスを返すテスト用ツール
ハンドラ
  … 「この URL にはこの JSON / ステータスを返す」という台本の1行
フレーク
  … 同じコードなのに実行ごとに成功・失敗がぶれるテスト
TypeScript
import { http, HttpResponse } from "msw";
import { setupServer } from "msw/node";
import { render, screen, waitFor } from "@testing-library/react";
import { TaskList } from "./TaskList";

const server = setupServer(
  http.get("/api/tasks", () =>
    HttpResponse.json([{ id: "1", title: "ship" }])
  )
);

beforeAll(() => server.listen());
afterEach(() => server.resetHandlers());
afterAll(() => server.close());

test("成功時はタスク名が見える", async () => {
  render(<TaskList />);
  expect(await screen.findByText("ship")).toBeInTheDocument();
});

test("401 のときはログイン誘導が見える", async () => {
  server.use(
    http.get("/api/tasks", () =>
      new HttpResponse(null, { status: 401 })
    )
  );
  render(<TaskList />);
  expect(await screen.findByText(/ログイン/i)).toBeInTheDocument();
});

test("500 のときはエラー表示になる", async () => {
  server.use(
    http.get("/api/tasks", () =>
      new HttpResponse(null, { status: 500 })
    )
  );
  render(<TaskList />);
  expect(await screen.findByRole("alert")).toBeInTheDocument();
});

findBy* と getBy*

非同期で後から現れる要素には findByText（内部で待機）を使います。最初からあるべき要素には getByText です。loading のあとに ready へ変わる画面では、だいたい findBy が主役になります。

03

楽観更新の失敗とロールバックを断言する

▼

「一度進んだ UI」が戻ることを合格条件にする

Query 章の楽観更新は、サーバ応答前に画面を先に進める手法でした。テストで成功パスだけ見ると、失敗時にロールバックしないバグが残ります。手順は次のとおりです。

1. 初期表示は「未完了」
2. ユーザーがトグル（切り替え）する → いったん「完了」に見える（楽観）
3. MSW が PATCH を 500 などで失敗させる
4. 最終的にまた「未完了」に戻っている（ロールバック）

userEvent（Testing Library の操作ヘルパ）でクリックを再現し、waitFor で非同期の戻りを待ちます。

TypeScript
import userEvent from "@testing-library/user-event";

test("PATCH 失敗後は完了表示が元に戻る", async () => {
  const user = userEvent.setup();
  server.use(
    http.get("/api/tasks", () =>
      HttpResponse.json([{ id: "1", title: "ship", done: false }])
    ),
    http.patch("/api/tasks/1", () =>
      new HttpResponse(null, { status: 500 })
    )
  );

  render(<TaskList />);
  const checkbox = await screen.findByRole("checkbox", { name: /ship/i });
  expect(checkbox).not.toBeChecked();

  await user.click(checkbox);
  // 楽観的に一度チェックが付く実装なら、ここで一時的に checked でもよい
  await waitFor(() => {
    expect(checkbox).not.toBeChecked(); // 最終的にロールバック
  });
  expect(screen.getByRole("alert")).toBeInTheDocument();
});

成功パスも1本は残す

失敗だけテストすると、成功時に画面が更新されない退化に気づけません。MSW で 200 を返し、最終的に checked になるケースを対で持ちます。契約テスト（OpenAPI）は「形」、本章は「画面の振る舞い」——テスト設計章の薄いフロント結合層と同じ役割分担です。

04

ログアウト後に旧キャッシュが見えない回帰

▼

認証章の clear を、テストで忘れないようにする

認証 / キャッシュ章の要点は「401 やログアウトで Query キャッシュを空にする」でした。これは設計メモだけでは腐ります。回帰テスト（一度直したバグが戻っていないかを確かめるテスト）として、次のシナリオを固定します。

1. ユーザー A のタスク「secret-A」が表示される
2. ログアウト（または 401）する
3. ユーザー B として入り直す（MSW の応答を B 用に切り替える）
4. 画面に「secret-A」が出ないことを断言する

出てはいけないものには queryByText / findBy の否定、waitFor で「しばらく経っても現れない」を使います。

TypeScript
test("ログアウト後に前ユーザーのタスクが見えない", async () => {
  const user = userEvent.setup();
  server.use(
    http.get("/api/tasks", () =>
      HttpResponse.json([{ id: "a", title: "secret-A" }])
    )
  );
  const { rerender } = render(<App />);
  expect(await screen.findByText("secret-A")).toBeInTheDocument();

  await user.click(screen.getByRole("button", { name: /ログアウト/i }));

  server.use(
    http.get("/api/tasks", () =>
      HttpResponse.json([{ id: "b", title: "task-B" }])
    ),
    http.get("/api/me", () =>
      HttpResponse.json({ id: "b", name: "Bob", role: "user" })
    )
  );
  // ログインし直したあと（アプリの導線に合わせて操作）
  await user.click(screen.getByRole("button", { name: /ログイン/i }));

  expect(await screen.findByText("task-B")).toBeInTheDocument();
  expect(screen.queryByText("secret-A")).not.toBeInTheDocument();
});

面談で一言で言うなら

「画面の状態ノード（loading/error/empty/ready）をユーザー視点で断言する。API は MSW で台本化する。楽観更新は失敗時の戻りを必ず見る。ログアウト後に旧キャッシュが出ないことを回帰で止める。」
