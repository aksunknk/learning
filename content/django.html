01

Django とは何か — MVT と「電池付属」

▼

💡 Django = Admin・ORM・認証が最初から揃った Web 枠組み

Flask / FastAPI が「薄いコア + 自分で組み立て」なのに対し、Django は 管理画面・ORM・フォーム・ユーザー認証まで一体です。SaaS の社内向け画面や、古典的なサーバ描画、そして Django REST Framework（DRF）による JSON APIの土台として広く使われます。

MVT（Model / View / Template）

Model     … DB の表を Python クラスで表す（ORM）
View      … リクエストを受け、Model を使い、応答を決める
Template  … HTML を組み立てる（サーバ側レンダリング）

※ MVC の Controller に近いのが Django の View。
※ JSON API だけの場合、Template の代わりに Serializer が「表現」を担う（DRF）。

FastAPI との役割分担（頭の整理）

Web/API 章の FastAPIは API ファースト。Djangoはフルスタック寄りで、同じ REST でも「Admin で中を見る」「テンプレを少し直す」が近い。CS 案件では後者の接点が多いです。

💼 Tips

まず公式チュートリアルの Polls を一度通すと、以降の用語が定着します。この章は「用語と実務の見方」を圧縮した地図です。

02

プロジェクトとアプリ — どこに何を置くか

▼

💡 project = 設定の器、app = 機能の箱

django-admin startproject config が設定ルート、startapp billing がドメイン機能です。問い合わせ「請求がおかしい」はだいたい billing アプリの models / views を見ます。

DIRECTORY
mysite/
  manage.py
  config/           # settings.py, urls.py, wsgi.py
  billing/          # models.py, views.py, admin.py, urls.py
  templates/        # 共有 HTML（プロジェクト方針による）
  static/

urls の接続

# config/urls.py
urlpatterns = [
    path("admin/", admin.site.urls),
    path("api/", include("billing.urls")),  # DRF ならよくある
    path("", include("billing.urls")),
]

💼 Tips

未知のコードベースでは config/urls.py → include 先 → views の順で辿ると速いです。

03

settings と環境変数 — 本番で壊れない最低限

▼

💡 DEBUG・SECRET_KEY・ALLOWED_HOSTS・DATABASES は最初に確認

「ローカルでは動くが staging だけ落ちる」の多くは settings 差分です。秘密はリポジトリに書かず環境変数へ。

PYTHON
import os
DEBUG = os.environ.get("DJANGO_DEBUG", "False") == "True"
SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]
ALLOWED_HOSTS = os.environ.get("DJANGO_ALLOWED_HOSTS", "localhost").split(",")
# DATABASES は DATABASE_URL または ENGINE/NAME/USER/...

💼 Tips（CS）

「特定テナントだけ 500」→ その環境のログと ALLOWED_HOSTS / DB 接続先を疑う。コードより設定のことが多いです。

04

ORM とマイグレーション — 表をコードで表す

▼

💡 Model が「データの辞書」、migrate が「DB への適用」

問い合わせの「データが無い／古い」は、モデル定義と実レコードの両方を見ます。

PYTHON
from django.db import models

class Subscription(models.Model):
    customer_id = models.CharField(max_length=64, db_index=True)
    status = models.CharField(max_length=20)  # active / past_due / canceled
    plan_code = models.CharField(max_length=40)
    current_period_end = models.DateTimeField(null=True, blank=True)
    created_at = models.DateTimeField(auto_now_add=True)

    def __str__(self):
        return f"{self.customer_id}:{self.status}"
SHELL
python manage.py makemigrations
python manage.py migrate
python manage.py shell
>>> from billing.models import Subscription
>>> Subscription.objects.filter(status="past_due").count()

💼 Tips

filter / get / DoesNotExist / MultipleObjectsReturned は切り分けの定番語彙です。DB 章の SQL と対応づけて覚えると早いです。

05

Django Admin — 運用の第一画面

▼

💡 Admin は「非エンジニアでも触れる正規の覗き窓」になりうる

CS がデータを確認する経路として Admin が許可されている現場は多いです。登録・検索・権限を間違えると事故るので、list_display / search_fields / 権限は設計対象です。

PYTHON
from django.contrib import admin
from .models import Subscription

@admin.register(Subscription)
class SubscriptionAdmin(admin.ModelAdmin):
    list_display = ("id", "customer_id", "status", "plan_code", "current_period_end")
    list_filter = ("status", "plan_code")
    search_fields = ("customer_id",)

💼 Tips

本番 Admin での手編集は、可能なら「誰が・何を・なぜ」をチケットに残す。監査と再現性のためです。

06

ビューとテンプレート — HTML を返す道

▼

💡 View が文脈を渡し、Template が描画する

案件の「Django テンプレート改修」は、多くの場合ここです。文言・条件分岐・ループ・リンク先の修正が中心になります。

PYTHON
from django.shortcuts import render, get_object_or_404
from .models import Subscription

def subscription_detail(request, pk):
    sub = get_object_or_404(Subscription, pk=pk)
    return render(request, "billing/subscription_detail.html", {"sub": sub})
DJANGO TEMPLATE
{% extends "base.html" %}
{% block content %}
  <h1>契約 {{ sub.id }}</h1>
  <p>状態: {{ sub.status }}</p>
  {% if sub.status == "past_due" %}
    <p class="warn">お支払いの確認が必要です。</p>
  {% endif %}
{% endblock %}

💼 Tips

テンプレにビジネスロジックを書きすぎない。{% if %} が肥大化したら View か Model のプロパティへ。

07

フォームと CSRF — 入力の正しさと改ざん耐性

▼

💡 POST フォームには CSRF トークンが必須

Django はデフォルトで CSRF を守ります。トークン欠落は 403 になります。セキュリティ章の CSRF と対応づけてください。

HTML
<form method="post">
  {% csrf_token %}
  {{ form.as_p }}
  <button type="submit">保存</button>
</form>

💼 Tips（CS）

「保存ボタンを押すと 403」→ テンプレ改修で {% csrf_token %} が消えていないかを疑う。

08

認証の入口 — login_required と request.user

▼

💡 「誰のリクエストか」が全ての認可の起点

セッション認証では request.user、API ではトークンからユーザーを解決します。他人の契約 ID をURLに入れても見せない（IDOR 防止）はセキュリティ章と同型です。

PYTHON
from django.contrib.auth.decorators import login_required
from django.http import Http404

@login_required
def my_subscription(request, pk):
    sub = get_object_or_404(Subscription, pk=pk)
    if sub.owner_id != request.user.id and not request.user.is_staff:
        raise Http404()  # 存在を隠すなら 404 も選択肢
    return render(request, "billing/subscription_detail.html", {"sub": sub})

DRF への橋、ログと shell による切り分け、テンプレート改修の安全な進め方。

09

Django REST Framework — JSON API への橋

▼

💡 DRF = Django ORM の上に載る REST 道具箱

Web/API 章の REST を、Serializer（入出力）と ViewSet（CRUD）で実装します。withham 型の構成（/api/ + JWT）は典型例です。

PYTHON
from rest_framework import serializers, viewsets
from .models import Subscription

class SubscriptionSerializer(serializers.ModelSerializer):
    class Meta:
        model = Subscription
        fields = ("id", "customer_id", "status", "plan_code", "current_period_end")

class SubscriptionViewSet(viewsets.ReadOnlyModelViewSet):
    queryset = Subscription.objects.all().order_by("-id")
    serializer_class = SubscriptionSerializer
    # 実際は permission / filter でテナント制限する

FastAPI との対比（再掲）

FastAPI は関数 + Pydantic、DRF はクラス + Serializer。どちらも「HTTP + JSON の契約」をコード化する点は同じです。先に Web/API 章を読むと吸収が速いです。

調査の型 — ログ・shell・URL 逆引き

▼

💡 CS の技術寄り対応 = 「再現 → ログ → データ → コード」

メール問い合わせをチケット化したあと、自分で追う順序を固定します。

チェックリスト

1. 再現手順（どの画面 / どの API / いつ頃）
2. ステータスコードとエラーメッセージ
3. サーバログ（traceback・request id）
4. Admin または shell で対象レコード
5. urls.py から view / serializer を特定

11

テンプレート改修の安全手順

▼

💡 文言・表示条件・リンクの3点以外は慎重に

CS 権限で触ってよい改修の多くは表示層です。課金判定や権限ロジックは開発チケットへ回す判断もスキルです。

やってよい例 / エスカレーション例

やってよい:
- 誤字、説明文、ヘルプリンク
- {% if status == "past_due" %} の表示強化
- メール文面テンプレの差し替え（運用ルールに従う）

エスカレーション:
- 価格計算、権限、他テナントのデータが見える疑い
- migrate が必要なスキーマ変更
- CSRF や認証まわりの無効化提案

💼 Tips

改修前後のスクリーンショットと、対象テンプレパスをチケットに残すとレビューが速いです。
